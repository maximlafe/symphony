# LET-738 `mode:plan` RCA

## Document Spec
- Objective: explain why Symphony produced a non-canonical ticket description in `mode:plan` and why the run appeared to get stuck in blocker paths.
- Scope: intake/routing contract, issue-description update guardrails, Linear 429 retry behavior, and a concrete remediation plan.
- Out of scope: unrelated ticket history, broader product redesign, and validations already documented in other reports.
- Evidence standard: every causal claim below is tied to a code or log anchor.

## Dependencies / Prerequisites
- Enabled `mode:plan` runs depend on `planning.swarm_assist_enabled=true` and the repo-local `plan-mode` entrypoint, with `swarm-iterate` invoked from that entrypoint when the gate is enabled.
- The planning handoff contract already requires a canonical short plan plus `artifact_path`, `artifact_revision`, and matching `plan_revision`.
- The swarm artifact must exist under `docs/reports/` and be attached to Linear before `Spec Review` handoff.
- The short plan remains authoritative if artifact and short plan diverge; this RCA does not propose any new policy layer for that precedence rule.

## Concrete Fix Plan
1. Repair the `mode:plan` short-plan writer so the generated description always includes `Document Spec`, `Verification Plan`, `Residual Risks`, and a non-empty `Acceptance Matrix`, with `Proof Mapping` when the work is execution/review oriented. Validation expectation: the canonical plan shape is present before any handoff attempt.
2. Preserve the existing `issueUpdate(description)` guard so `Required capabilities` cannot masquerade as acceptance evidence. The code already rejects that substitution in [dynamic_tool.ex:1955](/Users/lafe/.codex/worktrees/a262/Symphony/elixir/lib/symphony_elixir/codex/dynamic_tool.ex#L1955); the repair is to surface the failure earlier in the planning turn, not to relax the guard. Validation expectation: malformed or missing `Acceptance Matrix` still blocks before write.
3. Keep the Linear 429 handling bounded. The observed retry storm came from repeated milestone publication under cooldown, so the retry throttle in [ticket-movement-rewrite-final-e2e-report-2026-05-17.md:58](/Users/lafe/.codex/worktrees/a262/Symphony/docs/reports/ticket-movement-rewrite-final-e2e-report-2026-05-17.md#L58) should remain the baseline behavior. Validation expectation: 429 state-refresh and milestone retries converge through the existing continuation ceiling instead of looping; the current bounded retry / continuation behavior is preserved here and is not being redesigned.
4. Add explicit regression tests for both failure modes:
   - missing or malformed `Acceptance Matrix` blocks `issueUpdate(description)`;
   - 429 state-refresh and milestone retries converge through continuation ceiling instead of looping.
5. If the description writer still emits non-canonical text after the writer step passes its existing tests, stop the repair round and move the fix to the exact generator that assembles the short plan, not to downstream tracker plumbing. The downstream plumbing is already behaving as a gate, not a source of truth.

## Execution Order / Failure Modes
1. Apply the writer repair first, then rerun the shared baseline `SpecCheck` coverage and the existing `let_workflow_contract_test` contract coverage before touching tracker behavior. If the plan shape regresses, stop here and revert only the writer change; do not proceed to guard or tracker changes until the short-plan contract is green again.
2. Preserve the guard second, then rerun the shared baseline `SpecCheck` coverage and the existing `acceptance_capability_check_test` coverage that already proves `Required capabilities` cannot replace `Acceptance Matrix`. If the guard stops blocking malformed plan descriptions, treat that as a guard-only failure and keep the tracker layer untouched.
3. Apply the tracker retry handling last, then rerun the existing `workspace_and_config`, `orchestrator_status`, and `core` coverage that already exercise cooldown and continuation behavior. If the retry change regresses bounded convergence, revert the tracker-only change and keep the writer and guard changes only if their tests remain green. The current bounded retry / continuation behavior is preserved here and is not being redesigned.
4. Treat a writer-only failure as a contract-shape regression, a guard-only failure as a contract-enforcement regression, a tracker-only failure as a convergence regression, and a combined failure as a stop-the-line condition that aborts the repair round.
5. Do not advance to the next step unless the current step’s existing suite has passed; do not treat partial green results as completion for the whole sequence.
